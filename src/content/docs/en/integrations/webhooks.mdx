Webhooks work both ways:

- **incoming** — HTTP requests from external systems that perform operations in a workspace on behalf of an [API key](/en/integrations/api-keys): creating and updating issues, commenting on them, logging time, posting chat messages, creating and updating documents. A system that can't build our request body can still be connected as-is — [rules](#rules-for-a-foreign-payload-format) translate its own payload for you;
- **outgoing** — HTTP requests the platform sends you when something happens in the workspace.

Both are configured in **Settings → API + Webhooks**. The same page has an **Examples** section: pick an operation or an event and a real object, and get a ready request body with real identifiers substituted.

# Incoming webhooks

## Request format

There are two endpoints for the same call.

The main one — the key in the `Authorization` header:

```bash
curl -X POST 'https://<host>/_webhook/api/v1/webhook/action' \
  -H 'Authorization: Bearer fus_myworkspace_7f3a9c1d2e4f5061728394a5b6c7d8e9f0a1b2c3d4e5f60718293a4b5c6d7e8' \
  -H 'Content-Type: application/json' \
  -H 'Idempotency-Key: 3f29a1d2-6b1a-4e51-9b0a-6a1c9d8e7f21' \
  -d '{
    "action": "issue:create",
    "space": "FUSIO",
    "title": "Sync failing for tenant X",
    "description": "Steps to reproduce:\n1. Open integration settings\n2. Click Sync",
    "assignee": "dev@example.com",
    "priority": "high"
  }'
```

The second one — the same key right in the path, for senders (some no-code services, for example) that can only configure a URL, without custom headers of their own:

```bash
curl -X POST 'https://<host>/_webhook/api/v1/webhook/k/fus_myworkspace_7f3a9c1d2e4f5061728394a5b6c7d8e9f0a1b2c3d4e5f60718293a4b5c6d7e8' \
  -H 'Content-Type: application/json' \
  -d '{"action": "chat:post", "space": "64f10a1b2c3d4e5f6a7b8c90", "message": "Deploy finished"}'
```

A key in the path ends up whole in proxy and load-balancer access logs — use this variant only when a header isn't available. It also has a stricter rate limit (see below).

There is no workspace in the address: the key itself decides it. The exact addresses of your installation are shown in **Settings → API + Webhooks → Examples → Incoming request**, ready to copy.

<Image src={exampleIncoming} alt='Incoming request example' inferSize />
 The request body is always JSON in the shape `{ "action": "...", "<target field>": "...", ...operation-specific fields }`. `action` selects which operation runs, and the target is carried by one of three fields, a different one per operation: `space` (a project, a channel or a teamspace), `issue` (an issue) or `document` (a document). Which field goes with which operation is in the table below.

## Operations

| `action` | What it does | Required fields | Optional fields |
|---|---|---|---|
| `issue:create` | Creates an issue | `space` — project identifier (e.g. `FUSIO`); `title` | `description` (markdown), `assignee` (email), `priority`, `estimation` (number), `parent` (parent issue identifier) |
| `issue:update` | Updates an issue | `issue` — issue identifier (e.g. `FUSIO-42`) | `title`, `description`, `priority`, `assignee` (email, or `null` to unassign), `status` (status name) |
| `issue:comment` | Comments on an issue | `issue` — issue identifier; `message` | — |
| `issue:time_report` | Logs time on an issue, or edits an existing entry when `id` is given | `issue` — issue identifier; to create, also `employee` (email), `date` (`YYYY-MM-DD`), `hours` (greater than zero) | `description`; `id` — time report id: when present, only the fields you send are changed on that entry |
| `chat:post` | Posts a message to a channel | `space` — channel id; `message` | — |
| `doc:create` | Creates a document | `space` — teamspace id; `title` | `content` (markdown), `parent` (parent document id) |
| `doc:update` | Updates a document | `document` — document id | `title`, `content` |

Instead of `description` (on issues) and `content` (on documents) you may send a `body` field — the same markdown. Sending both at once is refused.

How references are resolved:

- A **project** (`issue:create`) is looked up by project identifier, and an **issue** (`issue:update`, `issue:comment`, `issue:time_report`, and `parent` for `issue:create`) is looked up by its own identifier like `FUSIO-42`.
- The **assignee** is looked up by email as a verified social identity on a contact.
- A **channel** (`chat:post`), a **teamspace** (`doc:create`) and a **document** (`doc:update`, and `parent` for `doc:create`) are only accepted as an internal id: a name or a title can be renamed, an id cannot. The easiest way to get one is **Examples → Incoming request**, with the target you need picked there.
- A **status** (`issue:update`) is matched by name, case-insensitively, among the statuses available to the issue's project's task type.
- A **time report** (`issue:time_report`): `employee` is looked up by email just like `assignee`; on an edit, `id` is checked against the issue from `issue`, so another issue's entry cannot be touched. The id comes back from the create call (`reportId`) and rides along in the outgoing `issue.time_reported` event.

`priority` values (case-insensitive): `urgent`, `high`, `medium`, `low`, `none` (alias: `no_priority`).

## Response and job status

Both ingest endpoints respond with `202` and `{ "jobId": "wh_..." }` on success — the request is accepted and queued, and processing happens asynchronously.

Checking a job's status:

```bash
curl 'https://<host>/_webhook/api/v1/webhook/job/wh_1a2b3c4d5e' \
  -H 'Authorization: Bearer fus_myworkspace_7f3a9c1d2e4f5061728394a5b6c7d8e9f0a1b2c3d4e5f60718293a4b5c6d7e8'
```

Response:

```json
{
  "jobId": "wh_1a2b3c4d5e",
  "status": "done",
  "createdAt": 1735689600000,
  "result": { "identifier": "FUSIO-142" }
}
```

`status` is `queued`, `done`, or `failed`. `result` is present only when `done`, and holds whatever the operation returned (for example, `identifier` for `issue:create`/`issue:update`, `messageId` for `issue:comment`/`chat:post`, `docId` for `doc:create`/`doc:update`). `error` is present only when `failed` and holds the failure reason. Any active key from the same workspace can check a job's status — it doesn't have to be the key that created the job.

Job records are kept for about a day — after that, `GET job/{id}` returns `not_found` even for a job that actually ran.

## Error codes

An error response is always JSON in the shape `{ "error": "<code>", "message": "<text>" }`.

| `error` | HTTP | Meaning |
|---|---|---|
| `unauthorized` | 401 | The key is missing, unknown, revoked, expired, issued for a different workspace, or does not have incoming webhooks enabled. The response is deliberately identical in all of these cases, so it doesn't hint at which keys exist. |
| `forbidden` | 403 | The key doesn't grant the operation named in `action` — it wasn't selected when the key was issued. The same code is used when the target lies outside the spaces the key is limited to. |
| `invalid_payload` | 400 | The body is missing `action` or the target field, or `action` isn't one of the known operations. |
| `payload_too_large` | 413 | The request body exceeds 1 MB. |
| `rate_limited` | 429 | The rate limit was exceeded. |
| `not_found` | 404 | The target was not found (no such project, issue, channel, teamspace or document). The same code covers a missing job in `GET job/{id}` and an unknown path. |
| `service_unavailable` | 503 | The account service is temporarily unavailable and the key could not be verified. The only intake error worth retrying. |
| `internal_error` | 500 | An internal error while accepting the request. |

Checks run in order, and each one only runs once the previous one passed: per-key rate limit → the key itself → request body and `action` → permission for the operation → idempotency → target lookup → enqueue. The one exception is `413`: an oversized body is rejected before the request reaches this chain at all.

The target is looked up before the job is queued on purpose: a typo in a project identifier comes back as a `404` right away, instead of as a failed job a minute later. If the lookup itself fails — the transactor is down, say — the job is accepted anyway and the target is checked when it runs.

## Rate limits

Request rate is limited with a sliding window, separately per key and per source IP — whichever limit runs out first applies. Defaults, requests per 60 seconds:

- key in the `Authorization` header — 60;
- key in the `/k/{key}` path — 20 (stricter: this form leaks the whole key into logs);
- source IP — 60.

The key limit is counted against the value presented, before it's even validated. The IP limit is only spent by requests whose key failed validation — it's a brute-force guard, and a valid key doesn't draw on it even when requests share an IP with someone else's failed attempts.

A `429` response carries these headers:

- `Retry-After` — seconds until it's worth retrying;
- `Retry-After-ms` — the same, in milliseconds;
- `X-RateLimit-Limit` — the limit for the current window;
- `X-RateLimit-Remaining` — requests left in the window (`0` on a `429`);
- `X-RateLimit-Reset` — when the current window resets, as Unix milliseconds (not seconds).

## Idempotency

The `Idempotency-Key` header takes any value you choose to be unique — your own event id or a UUID, for example. A repeated request with the same key from the same API key doesn't create a new job — it gets back the same `202` with the original request's `jobId`. Idempotency is keyed by the pair "API key + `Idempotency-Key` value" and is remembered for about a day; after that, the same value starts a new job.

Deduplication doesn't compare request bodies — sending the same `Idempotency-Key` with a different body still returns the original request's `jobId`, not a result for the new body. Pick a value that's unique to the specific event.

## Error and retry behavior

- Errors at the ingest step (`401`, `403`, `400`, `404`, `413`, `429`) are final. Retrying the same request unchanged won't help — fix the key, the body, the permissions, the target, or wait out the rate-limit window. Only `503` and `500` are worth retrying.
- After a `202`, processing is asynchronous. If the operation itself fails permanently (invalid references in the body, or the key lacking rights for the target space), the job is marked `failed` right away, with no retries — the reason is visible in `error` via `GET job/{id}`. The exception is a rejection from an internal rate limit — that job is retried on the schedule below.
- Transient failures (network issues, internal services being unavailable) are retried on a schedule: 30 seconds, then 1, 2, 4, 8 minutes — up to 5 attempts in total. If the operation still fails after that, the job is marked `failed` for good.


# Rules for a foreign payload format

Alertmanager, GitLab, Sentry, and similar systems send their own request body and can't build ours. For them there are separate endpoints that accept the sender's body as-is, and rules translate it into platform operations:

```bash
curl -X POST 'https://<host>/_webhook/api/v1/webhook/in' \
  -H 'Authorization: Bearer fus_myworkspace_7f3a9c1d2e4f5061728394a5b6c7d8e9f0a1b2c3d4e5f60718293a4b5c6d7e8' \
  -H 'Content-Type: application/json' \
  -d '{ ...your system payload... }'
```

There's also a path-key variant — `POST /_webhook/api/v1/webhook/k/{key}/in` — with the same caveats and the same limit as `/k/{key}`.

## Where to configure

Rules live on a specific API key. In **Settings → API + Webhooks**, the key's row has a **Rules** button; it shows up only when the key isn't revoked, has incoming webhooks enabled, and was issued by you. Other people's keys and rules aren't visible, not even to the workspace owner.

<Image src={webhookRules} alt='Key rules list' inferSize />

Rules are checked top to bottom; drag to reorder them. Each one can be switched off temporarily without deleting it. Edits take effect within about ten seconds — the service caches rules.

## From a template

The fast path is **From a template**. Ready-made templates cover Prometheus Alertmanager, Grafana, GitLab (push and pipeline), and Sentry. You only pick the operation and the target — say, "post to the `general` channel" — the conditions, fields, and sample body are already filled in.

<Image src={webhookRuleTemplate} alt='Creating a rule from a template' inferSize />

After creating it, you get the endpoint to put into the sending system. The key goes in as `Authorization: Bearer <key>`; for Alertmanager that's `http_config.authorization.credentials`.

<Image src={webhookRuleEndpoint} alt='Endpoint for incoming rules' inferSize />

## How a rule works

<Image src={webhookRuleEditor} alt='Rule editor' inferSize />

- **Sample request body** — the JSON your system sends. It's only used in the editor: it's where the path lists for conditions and fields come from, and it's what the preview is computed against.
- **Conditions** — checks against the whole body; all of them must pass. Operators: equals, not equals, exists, matches a regular expression, one of (a comma-separated list of values).
- **For each** — a path to an array in the body. The rule fires once per array element — a single Alertmanager notification can carry several alerts at once.
- **Item condition** — an extra check applied per element, with paths counted from the element itself. This is exactly how `firing` and `resolved` are separated within one group.
- **Operation** and **Target** — what to do and where. The choice is limited to the operations allowed for this key.
- **Fields** — the operation's fields, built from a template: `{{labels.alertname}}` is a path from the current element (or from the body's root, when there's no loop), while `{{$.externalURL}}` is always from the root. The **Insert value** button fills in a path from the sample body.
- **Preview** shows whether the rule matched, what value was found for each condition, and what the fields would resolve to.

## Response

A successful response is `202` with a list of the created jobs:

```json
{
  "jobs": [{ "jobId": "wh_1a2b3c4d5e", "rule": "6ab2be02925a16ab365dcd84" }],
  "skipped": []
}
```

Each job's status is checked via `GET job/{id}`, same as for ordinary incoming requests.

- If no rule matches, the response is still `202`, just with an empty `jobs`. That's a success for the sender — it shouldn't retry a request only because the event wasn't one you cared about.
- `skipped` lists rules that matched but couldn't run: `forbidden` — the operation or target is outside the key's rights, `not_found` — the target was deleted or renamed. A rule never grants more than the key itself already has.
- A single request yields at most 50 jobs. If the matching rules together would produce more, the whole request is rejected with `413`, and nothing is queued.
- The `Idempotency-Key` header isn't supported on these endpoints: one request turns into several jobs, so there's nothing to match a single key against.

Regular expressions in conditions run under a hard time limit, and a pattern longer than 200 characters or a checked value longer than 2000 characters is treated as no match. This guards against expressions that would otherwise hang the check.

An outgoing webhook is an address the platform `POST`s an event description to. They live in **Settings → API + Webhooks → Outgoing webhooks**, a section only the workspace owner sees.

## Events

| Type | Sent when |
|---|---|
| `issue.created` | An issue was created |
| `issue.status_changed` | An issue's status changed |
| `issue.assigned` | An issue's assignee changed |
| `issue.commented` | A comment was added to an issue |
| `issue.time_reported` | Time was logged on an issue |
| `issue.time_report_updated` | A time report was edited |
| `message.posted` | A message was posted in a channel |
| `document.created` | A document was created |

## Event body

A ready sample carrying real identifiers is built in **Examples → Outgoing event**:

<Image src={exampleOutgoing} alt='Outgoing event example' inferSize />

```json
{
  "action": "update",
  "type": "issue.status_changed",
  "actor": "author@example.com",
  "actorUrl": "https://fusion.example.com/workbench/acme/contact/64f10a1b2c3d4e5f6a7b8c8f",
  "url": "https://fusion.example.com/workbench/acme/tracker/FUSIO-123",
  "data": {
    "id": "64f10a1b2c3d4e5f6a7b8c91",
    "identifier": "FUSIO-123",
    "status": "In Progress"
  },
  "updatedFrom": { "status": "Todo" },
  "webhookId": "msg_2f1c9a7b",
  "webhookTimestamp": 1789084800,
  "organizationId": "9c858f36-6b1a-4d3a-8f2e-1a2b3c4d5e6f"
}
```

- `action` — `create`, `update` or `remove`;
- `type` — the event type from the table above;
- `actor` — email of whoever made the change, `actorUrl` — a link to their card;
- `url` — a link to the object itself: the issue, document or channel;
- `data` — the object's state, `updatedFrom` — previous values of the changed fields (on `update` only);
- `webhookId`, `webhookTimestamp` — delivery id and time, both part of the signature;
- `organizationId` — the workspace id.

Values in an event are the ones the incoming API accepts back, so an object can be sent straight in again: a status arrives as its **name** (`In Progress`), the assignee and the actor as **emails**, priority as a name (`urgent`, `high`, `medium`, `low`, `no_priority`), a channel as its id in `data.channel` (exactly what `chat:post` takes, with the name alongside it in `data.channelName`), and the parent issue of a comment or a time report as an identifier in `data.issue`. A value that could not be resolved stays an internal id.

## Signature

Deliveries are signed per [Standard Webhooks](https://www.standardwebhooks.com/). Headers:

| Header | Value |
|---|---|
| `webhook-id` | Delivery id |
| `webhook-timestamp` | Send time, Unix seconds |
| `webhook-signature` | Space-separated signatures, each `v1,<base64>` |
| `X-Webhook-Delivery-Id` | The same delivery id, for your logs |
| `X-Webhook-Attempt` | Attempt number, starting at 0 |

To verify: build the string `{webhook-id}.{webhook-timestamp}.{request body}`, take HMAC-SHA256 with the key — the bytes of the secret after the `whsec_` prefix, base64-decoded — and compare the base64 result against one of the signatures in the header.

```python
import base64, hashlib, hmac

def verify(secret, headers, raw_body):
    key = base64.b64decode(secret.removeprefix("whsec_"))
    signed = f"{headers['webhook-id']}.{headers['webhook-timestamp']}.{raw_body}".encode()
    expected = base64.b64encode(hmac.new(key, signed, hashlib.sha256).digest()).decode()
    return any(
        hmac.compare_digest(expected, part.split(",", 1)[1])
        for part in headers["webhook-signature"].split(" ")
    )
```

Sign the **raw** body, before parsing the JSON: a body re-serialized from an object almost certainly differs in whitespace and key order, and the signature will not match. Check `webhook-timestamp` too — rejecting a delivery older than a few minutes is sensible.

## Rotating a secret

An address can hold two secrets at once, and every delivery is signed with both — which is why `webhook-signature` may carry more than one signature. Rotating without downtime:

1. add a second secret — the receiver keeps verifying with the old one;
2. switch the receiver to the new one;
3. retire the old one.

The last secret cannot be removed: without a secret there is nothing to sign with.

## Where it applies

An empty whitelist means "every private space is excluded": an event from a private project or channel leaves the workspace only when that space is named explicitly. That way an address configured by the workspace owner never carries out the contents of private spaces the owner is not even a member of.

## Retries and auto-disable

- A delivery is retried on `408`, `409`, `425`, `429` and any `5xx`, and on network errors and timeouts (10 seconds per attempt).
- Schedule: 30 seconds, 1, 2, 4, 8 minutes — up to 5 attempts; after that the delivery is failed.
- Three failed deliveries in a row disable the address and mail the workspace owner. A successful delivery resets the counter.
- Up to 64 KB of the response is read and the body is ignored — only the status code matters.

## Requirements for the address

- `https` only. `http` is accepted only on a stand where the pod is configured to allow it.
- Private and internal addresses are refused: `127.0.0.0/8`, `10/8`, `172.16/12`, `192.168/16`, `169.254/16`, `100.64/10`, `0/8`, `224/4`, their IPv6 counterparts, and the names `localhost`, `metadata`, `*.internal`, `*.local`, `*.cluster.local`. The host is resolved twice — before the request and right before connecting — so the address cannot be swapped after the check.
- Redirects are not followed: a `3xx` counts as a failed delivery.

## If events don't arrive

- The address is disabled — check the switch next to the URL and the "last error" line on the address page.
- The event is not selected in the address's event list.
- The event happened in a private space that is not in the whitelist.
- The signature does not match — nearly always because it was computed over re-serialized JSON instead of the raw body.
- Nothing arrived at all — press "Send test event" on the address page: the result shows up immediately and the delivery lands in the log.
